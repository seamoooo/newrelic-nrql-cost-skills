# 検証記録・受入シナリオ

フロントマター、UIメタデータ、内部参照をローカルで検証した。以下は静的な受入レビューであり、独立エージェント試験や実アカウントでのMCP実行の記録ではない。

| シナリオ | 受入条件 | 静的レビュー |
|---|---|---|
| 直近30分の1サービス調査に7日分の全Logを取得 | 改善余地を指摘し、期間・サービスを絞る。削減率を捏造しない | 本体の範囲・正確性規則とquery-patternsに適合 |
| FROM Transaction SELECT count(*) のレビュー | 既定1時間と説明する。全保持期間スキャンとは言わない。目的不明なら効率判定を留保 | 本体とofficial-docsに適合 |
| filtered countと全件countを並べた比率のクエリ | 分母が変わる外側WHERE移動をしない | query-patternsの反例で確認 |
| backtickと除算を含むが範囲が限定されたクエリ | その構文だけを理由に全件スキャン・非効率と判定しない | 本体とofficial-docsに適合 |
| 同じクエリへLIMIT 1を追加 | 応答量とスキャン・CCUを区別する | 本体とquery-patternsに適合 |
| NRQLアラートの効率レビュー | SINCE/UNTIL/TIMESERIES/LIMITを追加せず評価設定を確認 | 本体とquery-patternsに適合 |
| MCP接続なし、アカウント指定なしで静的レビュー | 静的評価を完成させ、未実行と明示。全アカウント列挙で止まらない | 本体に適合 |
| NrComputeUsageにusageや帰属情報がない | 属性を捏造せずCCU未測定。count(*)を実行回数に読み替えない | measurementに適合 |
| ユーザーが30日分を必要としている | 探索の15分で最終回答を代用しない | 本体に適合 |
| 比較結果が同等、before=10 CCU、after=6 CCU | 対応が取れた同単位なら40%減。遅延の40%減ならCCU削減率とは言わない | measurementの算式に適合 |
| MCP呼び出しで外部LLMを使用 | MCPというだけでaCCUを加算せず、契約と実機能を確認 | 本体に適合 |
| レビューを依頼されE2Mが改善候補になった | 未作成メトリクスを実在扱いせず、E2Mルールを勝手に作らない | 本体とquery-patternsに適合 |

実利用で確認するもの：利用環境のMCPツール、アカウントごとの属性、提案NRQLの実行可否、結果の同等性、CCUの帰属・遅延、契約単価。これらはスキルの構造検証では保証されない。

## 追加の利用検証

スキルと参照ファイルを使い、以下の具体的依頼に対して静的レビューを実施した。これはNRQL実行成功・結果同等性・CCU削減を証明するものではない。

| 入力した依頼 | レビュー結果 | 反映した修正 |
|---|---|---|
| `FROM Log SELECT * SINCE 7 days ago LIMIT MAX`。checkoutの30分のERRORを確認。実行不要 | 改善余地あり。service.nameとlevelの存在を前提に、30分・checkout・ERROR・必要属性・50件の案を提示。抜粋と明示。CCU・金額・削減率は未測定 | LIMIT MAXも全件ではない点を追記 |
| `count(*)`と`average(duration)`を各々`FACET appName LIMIT 10`で取得。両方の上位を維持して統合 | 単純統合は同等ではない。最初の集計によってFACETが選ばれるため、両ランキングが必要なら2本を維持 | FACET統合の反例を追加 |
| 月初来CoreCCUを`FROM NrMTDConsumption SELECT sum(consumption)`で確認したい | 改善余地あり。累積値の合計を避けlatest(consumption)を提案。直後の空結果をゼロとしない | 月初来クエリと約3時間の生成遅延を追記 |
| 24時間の平均応答時間を`TIMESERIES 1 second`で確認したい | バケット上限を超える。粒度の見直しか分割の相談が必要。分割は実行数増加を伴う | 366バケット上限と粒度の例を追記 |
| before/afterをそれぞれ`SINCE 1 hour ago`で順次実行して削減率を出したい | 相対期間は同一母集団にならない。固定期間・実効時刻の照合後に比較。実行時間をCCUへ換算しない | タイムゾーン付き固定期間と丸めの注意を追加 |

根拠はreferences/official-docs.mdの公開公式資料。例示クエリは対象アカウントのスキーマと照合して使う。

## MCPを使った実利用検証

リポジトリの既存設定を使いNew Relic MCPへ直接接続し、tools/listで確認した読み取りツールから11本のNRQLを実行した。動画再生イベントの固定期間を対象とし、以下を確認した。認証情報・生テレメトリ・実クエリ文字列はこのスキルリポジトリに保存していない。

- 再生試行・開始の個別集計とfilter()による統合集計が一致した。
- SELECT *と必要4属性の取得は、同じ全行について必要属性の多重集合が一致した。count(*)とLIMITの関係も確認し、抜粋同士の一致を全件一致と誤認していない。
- NrdbQueryの性能記録とNrComputeUsageの利用量記録を正確なクエリ文字列で照合した。各対象について成功1実行・利用量1記録を確認した。
- 属性の絞り込みでは結果JSONサイズが減ったが、検査件数と記録CoreCCUは変わらなかった。集計統合では別々の2実行の合計と統合1実行を比較した。
- このMCPのNRQL戻り値は結果行のみで、性能情報や実効開始・終了時刻を含まなかった。性能は別イベントから観測し、実効時刻は応答から検証できないと扱った。

各クエリ1回の小規模な観測であり、一般的な性能倍率・請求額・今後の削減率は保証しない。月初来・アラート・Metric置換・高カーディナリティの全件取得は今回の実行検証に含まない。

## 運用クエリの実行検証

11本のNRQLを読み取り実行し、次を確認した。実環境の識別子・利用者情報・生の計測値は掲載していない。

- NrConsumptionのスキーマを確認し、CoreCCUの全体合計、機能別の内訳、1時間ごとの推移を取得した。
- 利用者別の内訳を照会し、分類属性の欠落と全体との差を確認した。
- 対象アプリのAPMメトリクスの存在を確認し、応答時間・毎分の処理件数・エラー比率を個別に取得した。
- APMの複数指標を1本へまとめた結果と、個別クエリの各時間バケットの値を照合した。
- Transactionイベントとの比較では件数と平均値に差があったため、メトリクスへの無条件な置換は採用していない。

APMの比較期間ではエラー比率は0だったため、非ゼロのエラーや分母が0の区間の挙動までは検証していない。UIの更新間隔・Optimizerの推定効果・アラートの発報挙動は今回のクエリ実行で計測したものではない。設定変更は行っていない。
