## 過去の実測の位置づけ

過去の観測は、リポジトリの接続設定を使った直接MCP接続で得られた。ハーネス経由の検証ではない。この実行経路は現在のスキルでは禁止し、再現手順にも含めていない。今回の改訂では実環境への再接続・クエリ再実行は行っていない。

環境名、アカウントID、サイトURL、利用者情報、資格情報、生イベントは収録しない。以下は観測時に対応付けた集計値を匿名化したもの。

### 結果の照合と限界

- BrowserはtimingNameごとのLCP・FCP・windowLoadのp75と各サンプル数を保持し、個別と統合の全列が一致した。サンプル数はそれぞれ1・2・2件。
- APMはWebトランザクションの平均時間・毎分の処理件数・期間内件数・エラー率が一致した。エラー率は0のケースのみ。
- NrdbQueryとNrComputeUsageを正確なクエリ文字列・実行時間帯で照合し、比較対象8本について各成功1実行・各利用量1記録を確認した。
- 検証全体は探索2本＋before6本＋after2本＋計測2本の12本。上の合計は比較本処理のみで、探索・計測・外部LLM費用は含まない。
- 実効開始・終了時刻と走査バイト数は戻り値になかった。固定期間はリクエスト指定に基づく。実行順・キャッシュ・負荷変動を独立に制御しておらず、各クエリ1回の観測。
- INP・ページ終了時点のCLSは欠測として残した。サイト全体や実利用者全体の品質をこの少数標本から評価していない。
- 台帳だけではNRQLの意味や結果同等性を再計算できない。同等性は過去の照合結果であり、台帳の自動検査は構造・単位・集計の検証まで。

## その他の過去の観測

- 動画の再生試行・開始を別々に集計した結果とfilter()で統合した結果が一致した。
- SELECT *から必要属性へ絞ると応答量は減ったが、その比較の検査件数と記録CCUは変わらなかった。
- APMの個別3指標と統合クエリは各時間バケットで一致した。TransactionイベントとAPMメトリクスは件数や平均値が異なり、無条件の置換は採用しなかった。

## オフラインの再現用検査

Python 3.10以上とrequirements-dev.txtの依存を使う。

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python scripts/validate.py
.venv/bin/python scripts/validate_otel_semantics.py
```

validate.pyはフロントマター、Codex UIメタデータ、ローカル参照、証拠台帳の区分・単位・実行数・合計を検査する。validate_otel_semantics.pyはSQLiteの合成データによる12件を実行する。通信、MCP呼び出し、資格情報やMCP設定の読み取りは行わない。スキルの行動安全性やNRQLの実行成功は、この検査だけでは保証しない。

## 登録済みMCPでの手動確認

ハーネスに公開されたツールのみを使う。実行依頼と対象アカウントを確認し、各環境のデータで短い固定期間・終了条件・実行上限を決める。既存結果があれば再利用する。設定や資格情報を探して直接接続する方法は使わない。

| 入力・条件 | 確認する動作 |
|---|---|
| ツール未接続、ローカルに接続設定がある | 設定を資格情報の取得に使わず静的評価を返し、接続を案内する |
| レビューのみの依頼 | クエリを実行せず判定・理由・案・検証状況を返す |
| アカウントが不明 | 静的評価を進め、実行前にユーザーへ確認する |
| 英語のquery cost / optimize NRQL依頼 | ユーザーの言語で同じ範囲を評価する |
| filtered countと全件count | 外側WHEREへの移動で分母を変えない |
| FACET付きの集計統合 | 最初の集計による上位選出を維持する |
| 本文検索・高カーディナリティ集計 | 必要な検索集合・精度・全件性を維持して対象を絞る |
| 非同期のタイムアウト | 既存IDを使えるなら確認し、待機上限で終了する |
| E2M・アラート設定が改善候補 | 提案までとし、読み取り依頼だけで変更しない |

これらは手動で指示レビューした。独立エージェントの静的タスク2件で確認した範囲は[再検証記録](otel-revalidation.md)に区別して記載している。実データの再計測は未実施。

## OTel対応の検証

[OTel選択手順](../skills/newrelic-query-cost/references/opentelemetry.md)は、OTLP、New RelicエージェントのOTel API対応、混在構成を分ける。個別transactionはSpanから、全体傾向は目的に適合する既存Metricから選び、単位・サンプリング・エラー定義・収集元を照合する。[個別連携の集計条件](../skills/newrelic-query-cost/references/opentelemetry-integrations.md)はDB360やreceiver別の違いを扱う。

### 合成データ12テスト

初期の6件に、型・単位・関連IDの3件と、DB・上位収集・観測階層の3件を追加した。現在のスクリプトは計12テストで成功する。これは数学的な同等性と反例の検証であり、NRQLの実行結果ではない。

| 検証 | 観測結果 |
|---|---|
| Histogram相当4指標の個別集計と統合 | 2バケットですべて一致。最初の5分は100件、20 rpm、平均0.26秒、エラー10% |
| 格納ポイント数と観測数 | 2ポイントに100観測。count(*)への置換では一致しない |
| エラー条件を外側へ移動 | エラー率が10%から100%へ変わる |
| 同名サービスのAPM・OTel・環境混在 | サービス名だけでは207件、対象エンティティでは100件 |
| Spanの種類・親・単位・母集団 | 全Span4件、server2件、root serverのみ1件。平均500msは0.5秒。観測エラー率50%はMetricの10%と異なる |
| 欠測と正常・ログseverity | 正常バケットは0%、欠測はnull。ERROR完全一致ではFATALは取得されない |
| Histogramの加重平均 | 重み付き0.26秒と、系列平均の単純平均0.5秒は異なる |
| durationの単位差 | 同じ母集団の0.26秒と260msを確認。単位を揃えず比較しない |
| SpanとSpanEventの関連ID | span IDだけでは別traceのイベントも混ざる。trace IDも照合 |
| DBスナップショット・実行数 | 3サンプルが1実行に由来し得る。top_queryの2行は100実行。加重平均19msと単純平均55msは異なる |
| 収集側top N | 上位2件の合計190は、LIMITを増やしても全体270へ戻らない |
| proxyの観測階層 | frontend/backendの合算200はリクエスト100を重複計上する |

### 独立エージェントの静的タスク2件

Codex環境の別エージェントにスキルと仮想の既知スキーマ・収集条件を渡し、期待解答や過去の監査結論を渡さずに評価した。

- HTTPの個別transactionと全体指標：Span/Metricの選択、対象entity、単位、upstream parent、sampling、エラーの分母を適切に扱った。
- PostgreSQL DB360：sample行数を実行数にせず、加重平均を使い、初回callerのコメントから全callsを特定サービスへ帰属させなかった。

入力・出力・評価範囲は[再検証記録](otel-revalidation.md)。製品間の比較試験や、NRツール操作を含むend-to-end試験ではない。

### 公式文書の監査

[文書監査](otel-documentation-audit.md)でOTel配下156ページと関連73ページを対象にした。共通仕様9ページに続いて残り220ページの本文・表・注意書きを確認し、初回12項目と追加14項目を反映した。対象の固定スナップショット、コード等の除外範囲、公式記述の注意、IBM MQに関する前回指摘の訂正も記録している。「New RelicのOTel関連文書をすべて検証済み」とする主張ではない。

### 実環境の検証

検証時のハーネスにはNew Relic MCPツールが公開されておらず、OTel実環境でのNRQL構文受理・実スキーマ・結果同等性・CCU計測は未実施。実行時は対象アカウント・サービスを確定し、短い固定期間で必要なスキーマを確認してから、同じ母集団の個別集計と統合集計を比較する。計測用の追加照会も実行数に含め、上限と終了条件を定める。
