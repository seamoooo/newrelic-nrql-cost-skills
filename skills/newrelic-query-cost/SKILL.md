# New Relic Query Cost

New Relic MCPのクエリを、得たい答えに対して必要な負荷かという観点で判断する。NRQLの見た目だけでCCU・料金・削減率を断定しない。通常は日本語で答える。

## 最初に確認すること

提示されたクエリまたは実行予定から、調査目的、対象アカウント・サービス、期間、用途（単発調査／繰り返し実行／アラート）を把握する。既知の情報を再質問しない。クエリだけでも静的評価は進められるが、不明な対象や実行頻度を推測で補わない。

判断基準の根拠は [references/official-docs.md](references/official-docs.md) の公開公式ドキュメントで確認する。個別の改善例が必要なら [references/query-patterns.md](references/query-patterns.md)、実測が必要なら [references/measurement.md](references/measurement.md) を読む。

## 実行前に評価する

次を目的と照合する。高負荷でも要求された分析に必要なら、その理由と削減した場合に失う情報を示す。

- **データ範囲**：実効時間範囲、アカウント数、イベント型、サービスやエンティティの絞り込み。通常のNRQLでSINCEを省略すると既定は直近1時間であり、無期限ではない。MCP引数やダッシュボードの上書きがあればそちらも確認する。アラートは時間句の追加ではなく集約ウィンドウ・評価設定を見る。
- **処理量**：大きなLog/Span、不要なJOIN・サブクエリ・COMPARE WITH、過剰なFACETの組み合わせや時系列粒度。結果行数、実行時間、検査イベント数、スキャン量、CCUは別の指標として扱う。
- **繰り返し**：ポーリング、同じ結果を得る複数クエリ、ページング、再試行、複数アカウントへの展開。GraphQLのバッチ化でHTTP回数が減っても、内包するNRQLの実行回数が減るとは限らない。
- **返す情報**：SELECT *や大きな応答は転送量・トークン・読解負担を増やす。必要な属性や明示的LIMITに絞れるが、LIMITだけでスキャン量やCCUが減るとは保証しない。必要な全件調査を黙って上位N件に変えない。LIMIT MAXも無制限ではなく、FACETクエリはLIMIT省略時にも件数制限がある。集計をまとめる際はFACETの選出基準が変わらないかも確認する。
- **代替と正確性**：既存Metricで同じ指標・母集団・単位・粒度を得られるなら候補にする。Metricが常に安いとは決めつけない。filter()のWHERE移動で比率の分母、ゼロとnull、複数集計の対象が変わらないかを確認する。backtickや除算だけを根拠に非効率とは判定しない。

## MCPでの動き方

利用可能なNew Relic MCPツールの名前・引数・戻り値を実際に確認する。特定サーバー名やexecute_nrql_query等の存在を前提にしない。現在のツール一覧に見当たらなくても、リポジトリに既存のMCP接続設定があれば接続可否を確認してから未接続と判断する。設定や認証情報は出力・コミットしない。接続がなければ静的評価と未実測の改善案を完成させる。アカウント選定が必要な実行だけ、対象が解決できるまで待つ。

レビューだけの依頼では、本番データにクエリを実行しない。調査の実行も依頼されているなら、その範囲内で読み取りを進め、コスト確認だけのために重い元クエリを再実行しない。既存結果・既知のスキーマを再利用し、必要な場合だけ対象データ型を短い範囲でkeyset()等により確認する。全アカウントや全データ型の総当たりを避ける。

探索用の短い期間と本来の分析期間を区別する。要求が30日なら最終回答は30日で評価し、15分の試行を代替回答にしない。比較測定には同じ固定期間を使い、戻り値の実効開始・終了時刻も照合する。MetricやTIMESERIESでは時間範囲の丸めがあり、同じSINCE/UNTIL文字列でも比較対象が一致するとは限らない。

クエリ実行計画には、実行数の見込みと、何が分かれば止めるかを含める。範囲拡大・再試行は未解決の仮説がある場合だけ行う。タイムアウトで結果が不明なら、実行状態を確認できる場合は先に確認し、同じ高負荷クエリを無条件に再送しない。複数アカウントへの並列展開は必要な対象だけに限定する。

E2M作成、アラート・ダッシュボード・収集設定の変更は改善候補として示す。レビューや読み取り調査の依頼を、設定変更の許可として扱わない。

## 判定と回答

次のいずれかを、根拠と確度とともに示す。機械的な点数や普遍的な「何日以上なら高コスト」という閾値は作らない。

- **効率的**：目的に見合う範囲・処理・実行回数で、明らかな重複がない。静的判断なら「静的評価」と明記する。
- **改善余地あり**：同じ答えを維持できる無駄が見つかった。
- **高負荷の懸念**：広いスキャンや反復があり、必要性または実行計画の見直しが必要。実測済みの高CCUと区別する。
- **判断材料不足**：目的・実効範囲・頻度などが欠け、効率性を決められない。分かっている懸念と不足情報は答える。

回答は、判定、主な理由、改善クエリまたはMCP実行計画、検証状況・残る不確実性を簡潔にまとめる。改善案は実行済み／未実行、意味が同等／用途を限定した代替のどちらかを明示する。

実測があればbefore/afterの同じ条件での指標を表にする。計測値がない場合は、金額・CCU・削減率を「未測定」とする。Core CCU、Advanced CCU、外部LLMの料金を合算・混同しない。MCP経由というだけでNew Relic AIのaCCUが発生すると決めつけない。金額換算には対象契約の単価・課金条件が必要。
